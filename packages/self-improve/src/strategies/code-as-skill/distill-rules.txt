The loop. Trials run in waves: every task without a success gets one fresh trial with the newest library (where records/PROTOCOL.md says tasks open in batches, a task not opened yet gets its first in a later wave), and a session like this one runs between waves on every completed trial. No trial is running meanwhile. A trial is one episode of one task (records/PROTOCOL.md says whether a task's trials repeat the starting state). The objective: every task solved in the fewest trials, by a library that also works on tasks nobody has seen.

Inputs: records/PROTOCOL.md (evidence about something that changed is void after the change), records/INDEX.jsonl (one line per trial: task, library version, outcome, steps, cost, new or not), records/TASKS.md (goals and outcomes; UNSOLVED marks the targets), records/<trial>/ (summary.md, learned.md and learned/: what the sub-agent kept beyond the library it was shipped, prompt.md, result.json, history.md: the transcript, grep it; history.json has every call complete; its last reply holds the `## For the library` block), and your memory in library/memory/.

How to work. Reading more does not find more; comparing and counting does.
1. Cards. Every solved task without a card gets one this session (sub-agents with disjoint task lists).
2. Analysts. One sub-agent per task with new trials, given the task's whole history and the cards of solved tasks that share its subgoals. It writes notes/<task>.md itself: how things work, each claim with the observation that shows it; what worked, with the commands and the confirming observation; comparisons along every axis the records have: the same subgoal in failed and successful trials, results across library versions, time used against time available. From reading each new trial it also writes one row to library/memory/rows/<session>.jsonl: trial, task, version, success, subgoals (achieved or not, how), decisive (for a failure: the event after which success was impossible, and what could still have saved it), setbacks (other losses or mistaken beliefs, recovered or not), time (where the steps went), told (warnings and advice it had, followed or not), variant (the assignment: executed, partly, not, never reached). Causes in its own words; you merge them after counting.
3. Givens. List what the protocol and the inherited library assume and test each against the records. A claim is verified only over trials that could have shown otherwise, or by a trial that acted the cause and saw the effect; a memo repeating a memo is not a second observation.
4. Count, then decide. Run library/memory/metrics/ over all rows, rank failure causes by trials ended, and change only what addresses the top. Each change is a hypothesis with the metric it should move; the next session rules on it (kept, reverted, or extended with how many trials would settle it), using only rows whose variant was executed: a cause stays open until a variant addressing it has been executed.
5. Second wave, before writing: for each top cause, compare trials where the failing subgoal succeeded with ones where it failed, in any task and version; test the givens still open; settle contradictions. Spend the session's time here: the gate passing is not the end of the work.
6. Experiments that can be read: test a variant where its result shows early, on comparable starting states, rotated across trials, and never at the cost of what works: a procedure that achieved a subgoal stays in use, in its order, until its replacement has been seen working.

What ships:
- One package of small parameterized functions, as payload/lib/<package>/, imported as kinex.lib.<package>, with a docstring on every module and function that says what it does and what it returns. A procedure that worked in a trial becomes a function the brief and the task skills name; prose is for what code cannot do. A helper checked only against a stub ships as optional, next to the written procedure it does not yet replace. A function does only what its name says, returns after what it starts has finished, and returns one machine-readable outcome instead of printing it; every branch has been run offline against a stub. A recurring lesson becomes a guard in the function that needs it: the guard stops and says what it measured and what to do, and acts on its own only where recorded trials show that action working; a guard that fires in successful trials is a bug.
- Capability skills, one per family of things that work the same way or step many tasks share, plus a playbook: how things work (verified facts), the procedure with the package, failure modes ranked by trials ended, what to check before stopping, and, where a failure later turned into a success, the general step that made the difference (how the unfamiliar thing was probed, how a blocked approach was changed, how long it is worth trying). Rewrite them from the current evidence each session rather than appending, carrying forward every verified fact not refuted since: no version labels, no tables kept from earlier versions, nothing true of one task only.
- brief.md, at most fifteen lines and 2,000 characters (skill_check enforces both): which skill when, the completion rule, the memo contract.
- One task skill per unsolved task, payload/skills/task-<task>/SKILL.md, at most ten lines, its description stating the task's goal so that a worker given this task loads it: what failed every time and why, which skills apply, and the best-known procedure for each subgoal in its order. A procedure that worked on this task is stated plainly, with what to switch to after two failures. An untested change, including a procedure from another task's card, goes on exactly one `Try next:` line; everything else keeps the best-known procedure.

What you keep in library/memory/ (never shipped), each brought up to date every session:
- rows/: the analysts' rows.
- metrics/ and METRICS.md, the code's output, rewritten every session: one table per question, one column per library version, including per subgoal the trials that attempted and achieved it, per procedure.
- EVIDENCE.md, rewritten every session as one table keyed by fact: verified, refuted or open, what it rests on; an open question carries a cheap experiment and is mirrored into a skill; per failing subgoal, the candidate procedures with how often each was tried and worked.
- CHANGES.md: one section per session, earlier sections kept: the rulings on the inherited predictions, then this session's changes with their predictions.
- cases/<task>.md: one card per solved task: the goal, its subgoals in shared vocabulary, what worked per subgoal and what failed before, how often, what looks like luck; at most forty lines; no trial ids or run paths.

[[SCHEDULE]]

Rules: evidence only from the trials: never fetch, read or reconstruct the benchmark's, simulator's or tasks' code, documentation or data, or any external material, nor tell sub-agents to. Remove the errors and calls that recur without effect across trials. Do not break what successful trials relied on unless the replacement is shown better; a change motivated only by unsolved tasks stays in their task skills until other tasks support it. Write for a reader who has only the library: no trial ids in what ships. Before ending, call skill_check (the gate; a library that fails it never ships) and fix what it reports.

Memo contract (put it in the brief): every trial ends its final reply with at most ten lines headed `## For the library`: facts for this task's later trials; candidate facts for any starting state, tagged `observed` or `inferred`; field-experiment results as `HYPOTHESIS <id>: <result> (<what was observed>)`.
