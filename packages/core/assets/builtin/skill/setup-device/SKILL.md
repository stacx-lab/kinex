# Set up a device

## Choose the guide

Use the ordered Device guide roots in current context. Search all roots for
`<root>/<name>/DEVICE.md` before falling back to the first
`<root>/templates/<type>/DEVICE.md`. Resolve the name/type from existing
configuration and the user's facts before asking for missing information.

Read the selected guide's Setup and applicable Use sections. Start from its
Setup → Profile YAML or the profile generated by its setup script. Follow the
type guide for units, frames, command schemas and feedback; complete the supplied
driver scaffold's SDK hooks.

## Provision and register

Work in the resolved workspace's `devices/<name>/` directory. Copy the driver
and required support files there; avoid dependencies on packaged template paths.
Read connection, model and calibration settings from the sibling `profile.yaml`.
Shared vendor clients may live in workspace `lib/`.

Use Kinex core Python and paths from current context by default. Record SDK and
helper dependencies with `uv add --project <python.project> PACKAGE`. Use a
separate environment when required by the vendor stack or requested by the user;
record its absolute interpreter path in `access.driver.interpreter`. Otherwise
omit that field. Keep credentials in environment variables. For direct Python
checks, supply the context's core helper and workspace library paths through
command-local `PYTHONPATH`.

Write profiles with `profile_write`, declaring implemented actions and preserving
existing facts and provenance. Leave unknowns as `???`; mark missing calibration
with `kind=needed`. New devices remain unloaded; profile edits preserve existing
activation intent. Clear resolved requests explicitly with
`needs_calibration:null` in the relevant section.

Where the device has specific operating requirements, write a concise `## Use`
section in `devices/<name>/DEVICE.md`, as required by its type guide. This replaces
the type's Use section for that device, so include the applicable operating
contract and verified examples. Keep provisioning details in Setup.

## Implement the driver

Reuse the supplied driver and core helpers. Persistent drivers are the default;
`kinex.driver_protocol.run` handles correlated JSONL requests, concurrent calls
and process-exit cleanup. Keep SDK diagnostics off stdout, including during
imports. Choose `timeout_s` to cover the longest supported operation.
Adapt SDK units, axes and frames to the declared device contract. Return actual
observations; use the type's absence representation for unavailable measurements,
never invented values or echoed commands.

Implement `load`, `unload`, `status`, and the type's operations:

- Load acquires resources and waits for readiness, reusing healthy connections.
  Roll back partial startup on failure. Status only observes; ordinary operations
  must not restart failed services. Load/read must not initiate motion or clear
  faults.
- Validate commands before effects. Buffered writes replace pending references
  and return `{execution_id, state}` immediately, with measured state rather than
  an arrival claim. Follow the type guide for duration, expiry and stop behavior.
  Preserve acquisition timestamps; cached readings keep their original timestamp.
- Keep reads and stop responsive during writes. Protect shared SDK state with
  short locks and call `kinex.driver_protocol.check_cancelled()` between native
  operations. Do not hold locks needed by reads or stop across motion waits.
- Declared stop scopes include this device and all others actually affected.
  Unload stops within that scope and releases resources. Use
  `kinex.driver_protocol.release` to attempt independent cleanup stages even when
  one fails. Preserve cleanup handles, report errors, and make repeated cleanup
  harmless without opening connections. Keep owned child services in the driver's
  process group and stop/wait for them; close borrowed clients without terminating
  shared services.

Use `persistent:false` only for adapters requiring a fresh process per call.
They cannot retain connections, recordings or owned services between calls.
Release temporary clients without cancelling accepted asynchronous commands;
explicit unload performs the declared stop.

## Verify and activate

Check profile schema, imports and driver syntax without starting hardware. Use
focused mock checks for changed behavior, including conversions, invalid-input
rejection and lifecycle failures where relevant. Avoid unrelated test suites.

Registration ends unloaded unless activation is part of the authorized task.
Use the device tool's load/unload actions or `/load`; Python tools cannot change
lifecycle. Verify readiness with device status or `/ping`, then perform only the
reads, inference or motion checks the task requires. Reload persistent drivers
after changing code or cached configuration with `/reload <name>` or unload/load.
