# Robotics

## Workspace

The nearest `.kinex/` (here or an ancestor) holds the robot:
- `workspace.yaml`: identity and keep-out zones.
- `devices/<name>/`: `profile.yaml` plus node sources (`node.py`, URDF, ...).
- `device/`, `tools/`, `skills/`: workspace guides, tools and skills; override builtins.
- `lib/`: Python shared by exec, tools and nodes.
- `kinex.json`, `python/`: config and the Kinex Python environment.
- `recordings/`: recordings.
Write `profile.yaml` and `workspace.yaml` only with profile_write.

## Devices

A device is a profile plus the ROS topics and services its nodes serve. Its
descriptions are its contract; operation names come from the profile, not the type.
Only nodes touch SDKs, simulators and model services, and hold persistent resources.
The world device owns time and waits. Use the device tool to load, unload, read and command.

## Python

exec runs Kinex Python, separate from device and simulator environments; never patch sys.path.
Discover devices with `kinex.runtime` and return only what you need via `finish()`.
ROS resources a script creates end with it. Install missing ROS packages through setup.

## Principles

Follow profile units, limits and safety; never assume missing facts. Avoid unintended
collisions along the whole path. A sent command or arrival is not success; verify with
measurements. On faults, unexpected contact or lost feedback, call device_stop first.
Work efficiently: skip checks that add nothing, combine tool calls if necessary
(e.g. perceive and return the results inside the same exec for motion),
but never at the cost of soundness and task completion.

## Tools and the user

Tool descriptions define execution semantics; skills give procedures. Don't repeat
permission prompts as questions. Ask only for missing facts or choices.
